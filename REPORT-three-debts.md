## 2. Пункт 1 — Р-3: модель угрозы, правка, контроль прогоном

### 2.1 Модель угрозы — явно

**Актив.** Очередь задач KAIC и право её пополнять: задача — это исполнение
модели с доступом к MCP-инструментам, а в наборе blender-mcp есть
`execute_blender_code` (произвольный Python внутри проекта пользователя).

**Атакующий.** Произвольная веб-страница, открытая архитектором в браузере.
Не сетевой злоумышленник и не сосед по локальной сети: `127.0.0.1:4545` для них
недостижим. Именно страница — потому что она исполняется на той же машине и
обращается к петлевому адресу как к соседу.

**Канал.** Два, и они складываются:
1. **Отсутствие аутентификации** — любой запрос принимался. `fetch('http://127.0.0.1:4545/tasks', {method:'POST', ...})` со страницы ставил задачу.
2. **`CorsLayer::permissive()`** — ответ `Access-Control-Allow-Origin: *` снимал
   запрет браузера на ЧТЕНИЕ ответа. Без него страница могла бы «выстрелить и
   забыть»; с ним она читала `GET /tasks` — всю очередь задач пользователя.

**Что атакующий получает.** Постановку задачи KAIC от имени архитектора без его
ведома, и чтение того, чем он занят. Через `POST /tasks` текст задачи выбирает
атакующий, а дальше задача идёт обычным путём — включая запрос вызова инструмента.
Гейт на инструменты (§5) здесь спасает: исполнение упрётся в `WaitingForHuman`.
То есть Р-3 не даёт немедленного исполнения кода, но даёт **чужой ввод в систему,
на выходе которой стоит человек, привыкший подтверждать свои же задачи.**

**Чего атакующий НЕ получает** (чтобы не раздувать оценку): доступа к файлам
напрямую, к токенам, к самому LM Studio, и исполнения инструмента без нажатия
человека.

**Границы модели.** Не рассматривается злоумышленник с локальным исполнением кода
на машине: он читает переменную окружения и обходит любой токен. Против него
защиты нет и в этой правке не появилось — это честная граница, а не упущение.

### 2.2 Правка

**Аутентификация.** Новый модуль `src/control_auth.rs`.

* Секрет — из переменной окружения **`KAIC_CONTROL_TOKEN`**. Это переиспользование
  уже существующей в проекте конвенции, а не новый механизм (**критерий 1.4**):
  Telegram Bridge читает `TELOXIDE_TOKEN` из окружения, а `config/telegram.yaml`
  прямо пишет «ТОКЕН ЗДЕСЬ НЕ ХРАНИТСЯ». Второй способ хранить секрет — это второй
  способ его потерять.
* **Анонимного режима нет.** Без переменной процесс не стартует. Наличие режима
  «работать без пароля» означало бы, что дыру можно вернуть забывчивостью.
* **Гарантия типом, не дисциплиной.** `ControlToken` — приватное поле, публичного
  конструктора нет; `build_router(state, token: ControlToken)` принимает его
  обязательным аргументом. Роутер без секрета невозможно собрать — не потому, что
  об этом помнят, а потому, что нечего подставить. Тот же приём, что
  `ApprovedToolCall` в гейте и `AdmittedAsset` в медиа-гейте.
* Сравнение за постоянное время; `Debug` написан руками и печатает
  `ControlToken(<20 символов, скрыт>)` — производный вывел бы секрет в первый же
  лог.
* Токен читается **первой строкой `main`**, до Resource Registry и до касания GPU:
  отсутствие секрета — отказ конфигурации, узнавать о нём надо за миллисекунды.

**CORS.** `permissive()` заменён явным списком из четырёх origin: `5173` и `4545`
на обеих формах петлевого адреса (браузер считает `localhost` и `127.0.0.1`
разными origin). Методы — `GET`/`POST`, заголовки — `content-type`, `authorization`.
CORS положен СНАРУЖИ проверки токена: preflight `OPTIONS` браузер шлёт без
`Authorization`, и отвечать на него должен CORS, а не 401.

**Почему токен первичен, а CORS вторичен** — записано в модуле: Origin подделывает
любой не-браузерный клиент (`curl -H 'Origin: …'`). CORS ограничивает браузер и
только браузер.

### 2.3 Контроль прогоном (критерий 4)

Отказ старта без секрета:

| Прогон | Результат |
|---|---|
| `env -u KAIC_CONTROL_TOKEN kaic.exe` | **exit 1**, `Error: переменная KAIC_CONTROL_TOKEN не задана…` |
| `KAIC_CONTROL_TOKEN=short kaic.exe` | **exit 1**, `Error: KAIC_CONTROL_TOKEN короче 16 символов (5 символов)…` |

Аутентификация на живом сервере:

| Запрос | Ответ |
|---|---|
| `GET /status` без заголовка | **401** + тело `Control Center API требует Authorization: Bearer …` |
| `POST /tasks` без заголовка | **401** |
| `GET /status` с НЕВЕРНЫМ токеном | **401** |
| `GET /status` с верным токеном | **200**, тело со `total_model_memory_mb`, `running_tasks`… |
| заголовок при отказе | `www-authenticate: Bearer realm="kaic-control-center"` |

CORS — тот же запрос, разный `Origin`, разный результат (это и есть Р2-контроль):

| Запрос | `access-control-allow-origin` в ответе |
|---|---|
| preflight `OPTIONS /tasks`, `Origin: https://evil.example` | **отсутствует** |
| preflight `OPTIONS /tasks`, `Origin: http://127.0.0.1:5173` | **`http://127.0.0.1:5173`** |
| `GET /status`, `Origin: https://evil.example`, верный токен | **отсутствует** — тело странице не отдадут даже при утёкшем токене |

Плюс 10 модульных тестов в `control_auth.rs` (пустой заголовок, неверный токен,
регистр схемы, голый токен без схемы, префикс и удлинение секрета, граница
минимальной длины, обрезка `\r\n` из PowerShell, `Debug` не печатает секрет).

## 3. Пункт 2 — диагностика: где именно теряется эффект

`systematic-debugging`, фаза 1 — прогоном и чтением, до всякой правки.

### 3.1 `cancel`: сигнал умирает на первом же шаге

```rust
async fn cancel_task(...) -> Result<StatusCode, ApiError> {
    if state.task_store.get(id).await?.is_none() { return Err(ApiError::NotFound); }
    state.task_store.set_status(id, TaskStatus::Cancelled).await?;
    Ok(StatusCode::OK)
}
```

Обработчик пишет слово в SQLite и отвечает 200. Дальше — поиск читателей:

```
$ grep -rn "Cancelled" src --include='*.rs'
```

Все попадания — это: сам обработчик, определение enum и его сериализация,
тесты, и не связанный с этим `Verdict::Cancelled` в Telegram-мосте.
**Ни `run_task_pipeline`, ни `run_agent_loop`, ни `agent_steps` за этим словом в
хранилище не ходят.** Канала между обработчиком и идущей задачей не существует
вовсе.

**Корневая причина названа: реестр задач умеет ХРАНИТЬ, но не умеет БУДИТЬ.**
Отмена записывалась в место, куда исполнитель никогда не заглядывает.

Отдельная тонкость, которая маскировала дефект. Коммит `e824a6f` («Stop a
finished generation from un-cancelling the task») чинил соседнюю проблему —
чтобы досчитавшаяся генерация не перезаписывала статус обратно в `Done`. Это
починило **бухгалтерию**, и снаружи выглядело как «отмена работает»: статус
оставался `cancelled`. Работа при этом продолжалась. Ровно тот случай, ради
которого К1 и записан.

### 3.2 `continue`: безусловный второй пайплайн

```rust
    state.task_store.set_status(id, TaskStatus::Running).await?;
    let refreshed = state.task_store.get(id).await?...;
    tokio::spawn(run_task_pipeline(...));   // безусловно
```

Проверки «а не идёт ли уже пайплайн по этой задаче» нет. Отсюда измеренное
`running_tasks` 1 → 2 и `generations` 1 → 2.

### 3.3 Почему вклинивание в идущую генерацию невозможно

Фаза 2 — чтение цикла целиком. `agent_steps` устроен так:

```rust
for step in 1..=MAX_TOOL_ITERATIONS {
    let request = GenerateRequest { messages: messages.clone(), ... };
    match session.generate(request).await? {
        GenerateResponse::Text(text) => return Ok(LoopOutcome::Answer(text)),
        GenerateResponse::ToolCalls(calls) => { ... }
    }
}
```

Для текстовой задачи цикл делает **ровно одно** обращение к модели и возвращается
на первом же `Text`. Точки, в которой реплика могла бы войти в идущую генерацию,
не существует: генерация — это один `await` на `POST /v1/chat/completions`.
Промежуточные шаги появляются только на пути с инструментами.

Это и есть архитектурный предел, и он того же рода, что измеренный в линии Bridge:
у `codex exec` вклинивания нет, а у `codex app-server` есть `turn/steer` — ровно
потому, что там ход состоит из событий, а не из одного ожидания.

## 4. Пункт 2 — правка и тесты: до/после, Р2-контроль

### 4.1 Тесты написаны ДО правки и упали на тогдашнем коде (критерий 6)

```
test cancelling_stops_the_generation_instead_of_waiting_for_it ... FAILED
  после отмены пайплайн жил ещё 638.8219ms — то есть досидел генерацию,
  а не прекратил её. Осталось генерации было ~650 мс

test continuing_a_running_task_does_not_start_a_second_generation ... FAILED
  left: 2   right: 1
```

Оба воспроизводят `АРХИВ-105` в миллисекундах: отмена не отменяет, реплика
удваивает.

**Честно про второй тест.** Первая его редакция утверждала «обращений к модели
ровно 1». Увидев, что он не проходит и после правки, я его переписал — и это тот
случай, который TDD запрещает делать молча, поэтому говорю прямо. Утверждение было
неверным по существу: измеренный `АРХИВ-105` дефект — это ОДНОВРЕМЕННОСТЬ
(`running_tasks` 1 → 2), а не общее число обращений. Последовательный
дополнительный шаг той же задачи — не дефект, а требуемое поведение. Тест теперь
меряет **пиковую одновременность** и отдельно требует, чтобы реплика была учтена.

### 4.2 Правка

**`TaskControl`** — реестр идущих задач в `AppState`: `Uuid → watch::Sender<bool>`.
`watch`, а не `Notify`, намеренно: он хранит значение, поэтому отмена, пришедшая
между двумя точками ожидания, не теряется.

`run_task_pipeline` отмечает задачу идущей до первого обращения к модели, снимает
отметку на любом исходе, и гоняет работу против сигнала:

```rust
let loop_result = tokio::select! {
    _ = wait_for_cancel(cancel_rx) => { return; }
    outcome = run_agent_loop(...) => outcome,
};
```

Проигравшее будущее **дропается**, а вместе с ним — запрос к модели и `Session`,
держащая `GenerationGuard`. Поэтому слот освобождается сразу.

`cancel_task` после записи статуса зовёт `control.cancel(id)`.
`continue_task` при идущей задаче дописывает реплику в контекст и возвращает
**202 Accepted**, не заводя второго пайплайна; пайплайн подхватывает реплику на
границе шага и продолжает **ту же** задачу (предел `MAX_HUMAN_FOLLOWUPS = 3`).

### 4.5 Архитектурный предел — названо прямо (критерий 8)

**Реплика НЕ входит в идущую генерацию.** Обоснование — §3.3: генерация это один
`await`, точки вклинивания нет. Что сделано вместо: реплика входит в **ту же
задачу**, тем же пайплайном, следующим шагом, последовательно; вторая генерация
не заводится.

**Что Control Center должен показывать вместо нынешней кнопки «продолжить»:**
пока задача идёт — кнопка называется **«дописать к задаче»** и рядом стоит
пояснение «будет учтено на следующем шаге»; ответ 202, а не 200, чтобы разница
была видна и машине. Кнопка «продолжить» в нынешнем смысле («возобновить
остановленную») остаётся только для задач в `WaitingForHuman`, `Paused`, `Failed`
— там она и работает как обещает. Одна кнопка на два разных действия — это то же
самое молчаливое расхождение, что и 200 на неисполненную отмену.

### 4.6 Заменённый тест — не скрываю

`work_finished_after_a_cancel_is_kept_but_not_as_the_answer` закреплял мир, в
котором отмена не останавливала работу и вопрос был лишь в том, куда положить
досчитанный результат. Такого результата больше не существует. Оставить тест
зелёным можно было бы только вернув дефект. Заменён на
`a_cancelled_task_has_neither_an_answer_nor_any_model_text` — свойство строго
сильнее: у отменённой задачи нет ни ответа, ни текста модели вообще.

## 5. Пункт 3 — гейт на вызов инструмента

**Главное: работа сделана раньше и запушена 2026-08-15.** Ворота 0 это установили,
постановка исходила из обратного. Ниже — сверка пяти шагов с кодом, прогоном
тестов, и то, чего в нём НЕ хватает.

### Шаг 1 — гейт как тип. **Есть.**

```rust
pub struct ApprovedToolCall { call: ToolCall, approved_by: Approval }
```
Поля приватны, публичного конструктора нет. Получить значение можно только через
`decide` (имя нашлось в allowlist) или `approve_by_human` (человек ответил «да»).
`execute_tool` принимает `&ApprovedToolCall` — сырой `ToolCall` не подходит по
типу. Обойти нельзя не потому, что все дисциплинированы, а потому, что в обход
нечего положить.

### Шаг 2 — allowlist, аннотации не в счёт. **Есть.**

Прогон, свежий:

```
test tool_gate::tests::an_empty_allowlist_asks_about_everything ... ok
test tool_gate::tests::only_an_exact_name_passes ... ok
test tool_gate::tests::no_name_heuristics_whatsoever ... ok
test mcp::tests::server_annotations_never_reach_the_decision ... ok
test mcp::tests::the_allowlist_defaults_to_empty_when_the_config_omits_it ... ok
```

Список пуст по умолчанию, сравнение имён точное (ни префиксов, ни масок, ни
регистронезависимости), аннотации сервера до решения не доходят — поле не
попадает в `ToolSpec`. Эвристик по именам нет, и это сказано в коде прямо:
`get_` не значит безопасно, `get_viewport_screenshot` читает экран.

### Шаг 3 — путь подтверждения. **Есть, кроме протухания.**

`describe()` кладёт в контекст сервер, инструмент и **аргументы целиком** с
указанием длины; тест `the_human_sees_the_arguments_whole` это стережёт.
Ответ человека — отдельный маршрут `POST /tasks/:id/tool-decision {"approve":bool}`.
При отказе пишется сообщение роли `tool` с текстом отказа — модель узнаёт.

**Согласование с правкой `continue` (требование постановки):** пути разные и
теперь не сталкиваются. Подтверждение идёт своим маршрутом `tool-decision`;
задача в этот момент в `WaitingForHuman`, то есть **не** «идущая», и `continue`
по ней ведёт себя как раньше — возобновляет. Реплика же в идущую задачу больше не
плодит второй пайплайн. До правки §4 два пути могли наложиться: `continue` по
задаче, ждущей решения, запускал бы вторую работу поверх первой.

**Протухание — решено: срока годности у подтверждения вызова НЕТ.** Обоснование,
а не умолчание. У Telegram-моста есть `approval_ttl_seconds: 900`, и там это
верно: черновик сообщения устаревает вместе с разговором, отправить старое
одобрение — навредить. У вызова инструмента иначе: задача заморожена в
`WaitingForHuman`, под ней ничего не меняется, аргументы зафиксированы в контексте
и показаны человеку целиком. Срок годности здесь добавил бы **новый молчаливый
отказ** — задачу, которая тихо стала неподтверждаемой. Час раздумий не делает
вызов менее верным.

### Шаг 4 — аудит. **Есть.**

`append_audit` дописывает (`OpenOptions::append(true)`) строку JSON:
`at`, `task`, `server`, `tool`, `tool_call_id`, `arguments` (целиком),
`approved_by`, `outcome`, `result`. Отказы человека пишутся тоже —
тест `a_human_refusal_is_written_to_the_journal_too`, вызов `append_audit` стоит
на обеих ветках (подтверждение и отказ).

### Шаг 5 — живой прогон. **НЕ ВЫПОЛНЕН СЕГОДНЯ.**

Говорю прямо, без смягчения: три сценария плюс контрольный на `GPTOSS20` +
blender-mcp я **не прогонял**. Что есть вместо и почему этого недостаточно:

* `АРХИВ-64` описывает живой прогон 2026-08-15: 57.4 с, два вызова, модель
  отреагировала на результат. Это чужая запись девятидневной давности, и по
  правилам этой же задачи она подлежит проверке, а не наследованию.
* Четыре ветки решения покрыты модульными тестами (выше), но модульный тест не
  проверяет связку с настоящим MCP-сервером.
* В дереве есть `mcp::tests::live_blender_mcp_lists_its_tools`, помеченный
  `#[ignore]` («требует установленного blender-mcp; запускать явно»).

Причина невыполнения: бюджет ушёл на пункты 1 и 2, а живой прогон требует поднять
LM Studio с `GPTOSS20` (12 073 MiB с оффлоадом 11 300 MiB) и четыре сценария
подряд. Это остаток долга, и он назван в §9.

## 9. Долги без срочности — с основанием квалификации

1. **Живой прогон гейта не выполнен** (§5, шаг 5). Основание квалификации —
   **замерено**: четыре ветки решения зелены модульно, но связка с настоящим
   blender-mcp сегодня не проверялась ни разу. Это НЕ «без срочности»: пока
   прогона нет, `АРХИВ-64` остаётся непроверенной записью, а по правилам этой
   задачи такие записи проверке подлежат.
2. **`kaic-ui` не знает про токен.** Основание — **замерено**: `GET /session`
   без заголовка отвечает 401, а `kaic-ui/src/api/controlCenter.ts` шлёт запросы
   без `Authorization`. То есть UI сейчас получит 401 на каждый запрос. Правка UI
   в три долга не входила, но это прямое следствие моей правки, и умолчать о нём
   нельзя. Срочность высокая.
3. **`main` опережает `origin/main` на 25 коммитов.** Основание — **замерено**
   (`git rev-list --left-right --count`). Секретов в них нет (§1.2). Не трогал:
   вне трёх долгов.
4. **Отмена не останавливает LM Studio, только KAIC.** Основание — **замерено**:
   в логе заглушки запрос остаётся в обработке после отмены, KAIC лишь перестаёт
   его ждать. Слот KAIC и `GenerationGuard` освобождаются сразу; вычисление на
   стороне LM Studio продолжается до своего конца. Границу называю прямо: KAIC не
   может прервать чужой процесс, а API LM Studio отмены не предоставляет.
5. **`a_cancelled_task_stays_cancelled_after_the_generation_finishes` теперь
   проходит тривиально.** Основание — **замерено**: он отменяет в середине
   генерации, а генерация после правки прерывается, так что гонки, которую он
   стерёг, в этом сценарии больше нет. Тест не удалён: гонка «ответ пришёл в
   миллисекунду перед записью статуса» остаётся возможной. Но стережёт он её
   теперь слабее, чем написано в его комментарии.
