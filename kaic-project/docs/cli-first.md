# KAIC: CLI-first

Основной пользовательский интерфейс KAIC — CLI. Существующий Electron Control
Center сохранён как дополнительный интерфейс; его развитие не является
приоритетом текущего этапа. Имя crate `kaic-tui` оставлено для совместимости.

## Архитектурное решение

`kaic-cli → ApiClient → существующий Control Center API → KAIC backend`.
Router, Scheduler, модельные адаптеры, хранилище и полномочия остаются в backend.
Новый исполнитель, оркестратор или собственная база сессий не создаются.
`experiments/kaic-terminal` — существующий самостоятельный эксперимент с GGUF;
он не переписан и не выдан за подключённый клиент основного backend.

Выбран построчный Rust CLI на существующих зависимостях. Это позволяет работать
без Electron, Node.js и нового UI-framework. Полноэкранный TUI может стать
последующим renderer того же клиента, если будет согласовано добавление
библиотек. Реализация не использует исходники OpenCode или Claude Code.

## Реализованный этап

- Исполняемый `kaic-cli`: offline-справка, чтение статуса/задач/истории,
  создание задачи из аргумента и интерактивный режим.
- Явный выбор задачи, новая беседа, продолжение допустимой задачи, пауза,
  отмена и polling выбранной задачи каждые две секунды.
- Список моделей с признаком загрузки, обработка ошибок и `/refresh`.
- Постраничный неизменяемый approval, полный просмотр перед разрешением,
  точный request ID в двух командах и запрет решений через pipe.
- Ограниченный UTF-8 ввод, раскрытие управляющих символов в ответах,
  штатный выход без изменения настроек терминала.

Подробные команды и требования окружения — в [README клиента](../kaic-tui/README.md).
Наличие клиента не означает проверенный запуск реальной модели: в этом этапе
проверки проводились на локальных HTTP-дублях, без загрузки моделей.

## Проверки и команда

Среда — текущий Artix Linux. Существующий Cargo cache использован offline.
Rust suite: 29 unit + 5 process + 3 HTTP integration = **37 passed, 0 failed,
0 ignored**. PTY: полный просмотр, запрет раннего разрешения, исходная задача
после переключения, неверный UUID, повтор, отказ, устаревание, отмена, `/quit`
и SIGINT прошли. Настройки termios после выхода совпали с исходными.
Дополнительно PTY-тест проверяет фактически выведенные поля и полную строку
аргументов снимка после удаления только переносов pager.

Из корня репозитория выполнены проверки crate `kaic-project/kaic-tui/Cargo.toml`:

| Команда Cargo | Результат |
| --- | --- |
| `build --locked --offline --bin kaic-cli` | exit 0, dev binary собран |
| `test --locked --offline` | exit 0, 37 passed |
| `clippy --locked --offline --all-targets -- -D warnings` | exit 0 |
| `fmt --check` | exit 0 |
| `python3 kaic-project/kaic-tui/tests/cli_pty.py /tmp/kaic-tui-client-check/target/debug/kaic-cli` | exit 0 |

Для Cargo использовались `CARGO_HOME=/tmp/kaic-audit-krrrb9ap/cargo-home` и
`CARGO_TARGET_DIR=/tmp/kaic-tui-client-check/target`. Первоначальные sandbox
ошибки TCP bind EPERM устранены разрешённым повтором локальных проверок;
ограничение sandbox не засчитано как дефект CLI или успешный тест.

Native-агент `tui_contract_tests` написал только процессные тесты;
`tui_independent_review` независимо прочитал реализацию. Ведущий реализовал
CLI, интегрировал изменения и выполнил проверки. Частный код внешним
провайдерам не передавался; `kirpich-agent` не участвовал.
Использованы навыки `kirpich-rust`, `kirpich-api`, `kirpich-test-strategy`,
`kirpich-security` и `kirpich-orchestrate`.
Reviewer не обнаружил конкретных новых P0/P1 дефектов, но тесты сам повторно
не запускал. SIGINT отправлялся процессу напрямую: нажатие Ctrl+C через
controlling terminal, EOF/Ctrl+D и раздельные комбинации TTY/pipe не проверены
PTY-тестом. Обычный pipe-ввод и отказ от approval через pipe покрыты Rust-тестами.

## Оставшиеся ограничения и следующий шаг

Потока токенов, отдельного session API, API skills/субагентов/стоимости и
workspace/diff нет. Автоматического восстановления исполнителя после аварии
нет. Полноэкранная компоновка, Unicode-ширина колонок, визуальный resize и
реальный эмулятор Wayland не проверялись: используется обычный построчный ввод.
Блокирующие HTTP-команды выполняются последовательно; во время запроса
обработка следующей строки ждёт ответа или timeout. Большой approval не
разрешается; допустима отмена задачи. Видимость текста не доказывает, что
человек прочитал его, а сам CLI не защищает скомпрометированный терминал.

Следующий практический шаг — smoke текущего CLI с отдельно запущенным backend
и уже доступной моделью, затем укрепление P1 lifecycle/recovery и, при наличии
потребности, контракт событий для потокового вывода. Новый TUI-framework и
дублирующие функции не являются условием использования CLI.
