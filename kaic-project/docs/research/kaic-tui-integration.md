# KAIC TUI: спецификация интеграции первого этапа

Дата: 2026-10-18. Реализовано ядро клиента; renderer и terminal lifecycle ожидают
согласования зависимостей. Решение и альтернативы:
[native-tui-design.md](native-tui-design.md). Подтверждения:
[tool-approval-contract.md](../tool-approval-contract.md).

## Границы компонентов

```text
Будущий terminal event loop / renderer
                ↓ команды и снимки
       App + безопасное представление
                ↓
    ApiClient → существующий HTTP API
                ↓
 Router → Registry → Scheduler → Backends → Agents → Memory → HITL
```

Последняя строка — намерение архитектуры KAIC, а не утверждение о полноте всех
её компонентов. Новый клиент не создаёт Scheduler, executor, хранилище истории
или разрешения параллельно backend. DTO и состояние отделены от терминальных
типов, что позволяет использовать контракт будущим desktop-клиентом.

## Существующие HTTP-контракты

Основание: активные `kaic-backend/src/control_center_api.rs` и `task_store.rs`,
включая незакоммиченный P0-патч. Префикса `/api` у маршрутов нет.

| Действие | Запрос | Поведение клиента |
| --- | --- | --- |
| Список / переоткрытие | `GET /tasks`, `GET /tasks/{uuid}` | Полные задачи с историей; без автоматического continue |
| Новая задача | `POST /tasks` | `{text, category:null, allow_manual:false}`; возвращает Task |
| Продолжение | `POST /tasks/{uuid}/continue` | `{message, allow_manual:false}`; App разрешает Done/Failed/Paused без pending approval |
| Пауза / отмена | `POST /tasks/{uuid}/pause`, `/cancel` | Явные команды; закрытие клиента не отменяет задачу |
| Решение | `POST /tasks/{uuid}/tool-decision` | Только `{request_id, approve}` после свежего GET и полного сравнения цели |
| Модели | `GET /models` | Реестр и loaded/context capacity, без выдуманного выбора модели |
| Состояние | `GET /status` | Бюджет памяти, busy models, active operation, running tasks |

`ToolApproval`: `request_id`, `task_id`, `execution_id`, `tool_call_id`,
`tool_name`, исходная UTF-8 строка `arguments`, сервер `command/args/peer_name`.
Неизвестные поля approval DTO отвергаются: новая семантика требует обновления
клиента. Неизвестные поля Task допускаются; неизвестный TaskStatus — ошибка
протокола. Запись истории с ролью инструмента не создаёт полномочий.

## Неизменяемое подтверждение

1. Открыть отдельный диалог с клоном полного текущего снимка. Он продолжает
   относиться к исходной задаче при смене выбора в списке.
2. Вывести все идентификаторы и поля сервера, все аргументы команды и точную
   строку аргументов инструмента. Escape/Bidi раскрываются видимо; обратные
   косые черты удваиваются, чтобы буквальный escape отличался от управляющего.
3. Одобрение требует фактического полного показа и двух отдельных действий.
   Отказ не требует чтения всех аргументов. По умолчанию Enter ничего не решает.
4. Изменение любого поля, исчезновение запроса, отмена или потеря связи делают
   открытый диалог устаревшим до нового явного открытия.
5. `ApiClient::decide` повторно GET-читает **исходную** задачу и проверяет полное
   равенство. Последующая гонка GET/POST остаётся под защитой серверного claim.
6. `busy` блокирует повторную команду. После неопределённого POST не повторять
   решение автоматически; сначала перечитать состояние и проверить результат.

Вызов `mark_approval_reviewed()` сейчас является контрактом будущего renderer,
не доказательством видимости текста пользователю. Нельзя считать безопасность
полного UI проверенной только по тестам reducer.

## Сеть, ошибки и исполнение

Адрес M1 — только HTTP loopback без credentials, path prefix, query и fragment.
`localhost` нормализуется; произвольный DNS/remote URL не допускается. Токен
минимум 16 печатных ASCII-байт, не выводится в Debug/ошибках. Будущая точка
входа должна брать его из `KAIC_CONTROL_TOKEN`, не из argv. TLS/remote API
потребует отдельного решения о доверии. Proxy/redirect/internal retry отключены.

Connect timeout 2 с, весь запрос 5 с; ответ не более 2 МиБ. Ошибки API имеют
фиксированный текст без тела ответа, URL и секрета. 401/403 отделены от 409;
неопределённый результат записи отделён от ошибки чтения. Длинная общая история
может превысить лимит: клиент безопасно откажет, пагинация backend пока отсутствует.

Будущий actor: одна операция сети за раз; refresh не перекрывает POST.
`receive_snapshot` обновляет данные, `success` завершает команду, `fail` помечает
связь потерянной и сбрасывает busy. Несвязанный refresh не должен сбрасывать
живой POST через `fail`. При параллелизации понадобятся operation ID и проверка
поколения ответа. Polling не объявлять streaming. POST никогда не повторять
автоматически; GET можно повторять с ограниченной задержкой.

## Сессии и восстановление

Первое чтение выбирает наиболее свежую задачу из серверного списка. Ctrl+N в
будущем UI создаёт пустой draft; обновление списка не возвращает старый выбор.
Поздний ответ Create не перехватывает новую сессию; новый текст не стирается
подтверждением отправки предыдущего. App не сохраняет draft на диск: после
выхода клиента несохранённый ввод теряется. История остаётся в backend SQLite.

После аварии backend статус Running не является доказательством живого worker.
Автоматический replay отсутствует. P1 остаётся частичным: Video-ветка выполняется
до общего cancel-select; crash reconciliation исполнителей не реализован.
Этот этап не меняет эти backend-пути и не обещает откат внешнего эффекта.

## Недоступные контракты и следующий этап

В API нет проектов, parent/child agents, skills, stream cursor, файлов/diff,
выбора конкретной модели, токенов и стоимости. Клиент не сканирует диск и не
подменяет эти возможности локальным исполнением. Markdown/code blocks пока
только безопасный текст; terminal layout, клавиатура, resize и RAII отсутствуют.

После согласования UI-зависимостей: Ratatui renderer/TestBackend, Crossterm
event loop/RAII/panic cleanup, сериализованный сетевой actor, полнота прокрутки
approval, startup/reconnect/shutdown/PTY/SIGTERM/resize tests. Затем — проверка
с реальным backend на Artix/fish и доступном терминале Wayland. Следующие backend
приоритеты: P1 recovery/cancel, пагинация задач, затем versioned event API.
