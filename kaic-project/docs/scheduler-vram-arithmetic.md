# Арифметика памяти Scheduler

Этап 2026-10-21, активный crate `kaic-project/kaic-backend`. Это учёт оценок
`vram_mb` из конфигурации, не измерение физической VRAM. Учёт RAM/VRAM по
устройствам и точный расход KV cache этот этап не добавляет.

## Причина и затронутые пути

Исходный `ResourceRegistry::always_loaded_vram_mb() -> u32` суммировал
оценки всех `always_loaded` моделей посредством `u32::sum()`. Его вызывают:

- `Scheduler::preload_always_loaded`: сравнение суммы резидентов с бюджетом
  до первой загрузки;
- `Scheduler::reachability`: оценка достижимости кандидатов поверх резидентов,
  вызываемая также из `log_reachability`.

Другие суммы `u32` находились в `fit_and_load` (все загруженные и защищённые
от LRU модели) и HTTP `/status` (снимок загруженных). `fits_in_budget` уже
использовал `checked_add`, но не мог исправить ранее переполненную сумму.
`sync_external_models` проверял прибавление каждой модели до обновления итога;
его бюджетная проверка была безопасной, но итог также переведён в `u64`.

В debug переполнение `u32::sum()` вызывает панику. В стандартном release
профиле Cargo без overflow checks сумма оборачивается по модулю 2^32:
требования могут выглядеть меньше действительных. Это влияет на допуск
предзагрузки, диагностику, необходимость вытеснения и выбор fallback.

Отдельная регрессия выявила предзагрузку резидентов при уже заполненном кеше:
проверка только суммы резидентов пропускала совместное превышение бюджета.

## Стратегия исправления

Одиночная оценка и бюджет остаются `u32`. Все совокупные оценки — `u64`:
`always_loaded_vram_mb`, `ReachabilityReport.resident_mb`, loaded/protected,
предзагрузка, discovery и `StatusDto.used_model_memory_mb`.
Сужения в `u32` и насыщения суммарных требований нет.

`ResourceRegistry::from_file` проверяет сумму **всех** записей через
`try_fold`/`checked_add`. Непредставимая в `u64` конфигурация возвращает ошибку.
После чтения оценки памяти неизменяемы: изменяться может только temperature.
Все последующие суммы выполняются по уникальным именам/ключам из этого же
реестра. Поэтому любая такая сумма не больше уже проверенной полной суммы,
и `sum::<u64>()` точен без переполнения. Это инвариант реестра, а не оценка
практически возможного числа моделей.

`fits_in_budget` дополнительно применяет `checked_add` в `u64` и сравнивает
результат с расширенным `u32`-бюджетом. При переполнении или превышении — отказ.
Проверка protected + candidate по-прежнему выполняется до первого вытеснения.
LRU, primary/fallback, ограничения busy и резервирования не менялись.

Предзагрузка под существующим `gpu_lock` проверяет resident + nonresident
cache до первого `load`. Загруженные резиденты не считаются дважды. При
превышении она возвращает ошибку и сохраняет кеш. Это не новый путь LRU:
обычное размещение продолжает использовать прежний выбор жертвы.

В reachability вычитается собственная оценка резидента из точной суммы,
которая по построению содержит эту оценку. Единственное оставшееся насыщение
памяти — отображение неотрицательного свободного остатка в логах: при
превышении бюджета показывается ноль. Оно не участвует в допуске моделей.

Имена JSON-полей `/status`, YAML и CLI-команды сохранены. На допустимых
состояниях значения `/status` по-прежнему не превышают `u32`-бюджет и читаются
существующим CLI. Внутренний `u64` также позволяет не оборачивать диагностику
некорректного снимка. `always_loaded_vram_mb` и поле отчёта — Rust-интерфейсы
внутри бинарного crate; их тип расширен для точного представления требований.

## Регрессии

Десять новых тестов в `scheduler_placement_tests.rs` используют синтетические
YAML и recording backend. Проверяются обычные суммы, несколько резидентов,
нулевые оценки, значения ниже/ровно/выше `u32::MAX`, отказ до backend-вызовов,
точность reachability, сохранение resident fallback, loaded/protected суммы
некорректного исходного снимка, легитимное LRU у границы и повторная предзагрузка
при заполненном кеше. Существующий тест `fits_in_budget` дополнен границами
`u32::MAX + 1` и переполнением самого `u64::checked_add`.

До исправления debug-прогон всего placement-модуля дал exit 101:
**9 passed, 6 failed**. В пяти тестах — `attempt to add with overflow`,
в шестом — ошибочный успех предзагрузки поверх кеша.

Тот же прогон в настоящем release-профиле проекта (`opt-level=3`, `lto=true`,
без изменения overflow checks) также дал **9 passed, 6 failed**, exit 101.
Вместо арифметической паники получены неверные результаты: сумма
`4294967295 + 1` стала **0**, предзагрузка вернула успех, а нулевая модель
загрузилась без необходимого вытеснения из переполненного исходного снимка.

## Оставшиеся границы

Защита от переполнения точна относительно неизменяемого реестра, а не
реального потребления моделей. Изменение оценок памяти в runtime потребует
повторного соблюдения проверенного инварианта общей суммы. Искусственные
loaded-снимки выше бюджета проверены только синтетическими тестами.
Конфигурация с суммой выше `u64::MAX` отвергается checked fold; материализовать
такой реестр из полей `u32` в тесте практически неприемлемо, поэтому эта
теоретическая граница обоснована кодом, не многомиллиардной фикстурой.

Реальные GPU, llama-server/GGUF, CUDA и optional EmbeddedBackend не
проверялись. Следующий этап — живой smoke CLI → backend → уже установленный
llama-server на имеющейся модели, с фиксацией версии runtime и фактических
ресурсных наблюдений; модели автоматически не скачиваются.
