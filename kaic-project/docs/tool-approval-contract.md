# Контракт подтверждения инструментов

Область: backend активного проекта `kaic-project/kaic-backend`.

## Основание решения

Ранее в историю записывалась вся группа вызовов модели, человеку показывался
первый ожидающий вызов, а обработчик решения выбирал последний. Кроме того,
идентификатор модели использовался для поиска старого разрешения без привязки
к серверу и аргументам.

Подтверждение теперь относится к отдельному серверному `request_id`. История
диалога служит для отображения и восстановления сообщений, но не выдаёт право
исполнения. Новые frameworks и зависимости для этого не требуются.

## Неизменяемая цель

Снимок запроса содержит:

- `request_id`: UUID, созданный backend;
- `task_id` и `execution_id`;
- `tool_call_id`: идентификатор протокола модели, не источник полномочий;
- `tool_name` и точную строку `arguments`;
- `server`: конфигурацию запуска `command`, `args` и имя подключённого сервера
  `peer_name`.

Снимок хранится в SQLite отдельно от текстового контекста. Изменение инструмента,
аргументов, задачи или сервера требует нового запроса и нового решения. Привязка
к конфигурации не является защитой от локального изменения самого исполняемого
файла сервера: установка MCP-сервера остаётся доверенной административной операцией.

## API

`GET /tasks/:id` возвращает текущий запрос в поле `pending_tool_approval`.
Клиент показывает его цель и передаёт именно полученный `request_id`:

```http
POST /tasks/:id/tool-decision
Authorization: Bearer <KAIC_CONTROL_TOKEN>
Content-Type: application/json

{"request_id":"<UUID из pending_tool_approval>","approve":true}
```

Для отказа передаётся `approve: false`. Старое тело `{"approve":true}`
отклоняется как неполное. Неправильный формат возвращает ошибку разбора запроса;
устаревшее, повторное, чужое или несовместимое с текущим состоянием решение —
конфликт. Неуспешное решение не должно запускать новый пайплайн.

Повторная доставка решения не означает повторное исполнение. Существующие
записи `tool_approval` из старой истории не преобразуются в разрешения.

## Порядок исполнения

Переход ожидающего запроса в принятое решение атомарен с проверкой статуса
задачи. Перед внешним вызовом разрешение одноразово переводится в состояние
исполнения. Сетевая операция выполняется после освобождения блокировки БД.
После переподключения сервер сверяется с сохранённым снимком.

Группа из нескольких вызовов модели отклоняется целиком до выполнения первого
вызова. Это намеренное ограничение безопасного минимального исправления.
Последовательные одиночные вызовы в разных шагах агентного цикла поддерживаются.

Обычный `continue` не заменяет решение по ожидающему запросу. Повторные ID,
выданные моделью, не должны наследовать разрешение предыдущего запроса.

## Отмена и сбои

Отмена инвалидирует ещё не начатые разрешения. Если отмена выиграла гонку до
одноразового захвата права исполнения, инструмент не запускается. Уже начатый
внешний побочный эффект может не поддерживать отмену или откат.

После одноразового захвата сбой процесса или потеря ответа не дают права
автоматически повторять инструмент. Политика гарантирует не более одной попытки
на разрешение; она не гарантирует ровно один внешний эффект.

Остановка и повторный запуск не должны воскрешать разрешения из истории.
Неопределённый исход инструмента требует отдельного решения человека.

## Проверка и совместимость

Обязательны регрессии для подмены первого/последнего вызова, точных аргументов,
чужой задачи, повторных и конкурентных решений, смены сервера, отмены и
повторного открытия SQLite.

Обычный набор выполняется командой `cargo test --locked` из каталога backend.
Сквозной тест
`control_center_api::approval_regression_tests::local_stdio_dispatch_executes_only_the_exact_once_approved_invocation`
использует настоящий клиент rmcp и собственный синтетический Python3 stdio-сервер.
Он помечен `ignore`, поскольку требует Python3 и отдельного временного рабочего
каталога для журнала аудита. После `cargo test --locked --no-run` нужно запустить
напечатанный Cargo тестовый бинарник по абсолютному пути из временного каталога
с аргументами `--ignored --exact <полное имя теста> --nocapture`.
Внешние модели, сеть и Blender для этого теста не требуются.

Изменение тела `tool-decision` намеренно несовместимо с прежними ручными
запросами без идентификатора. Откат к прежней логике возобновляет уязвимость;
при необходимости отката функциональности следует отключить выполнение
инструментов, сохранив данные подтверждений.

Вложенное дерево `kaic-control-center-reliability` этим изменением не обновляется
и требует отдельного переноса исправления перед использованием или слиянием.
